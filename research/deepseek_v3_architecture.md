# DeepSeek-V3: архитектура и основные компоненты

## 1. Основа архитектуры DeepSeek-V3

Архитектура DeepSeek-V3 основана на трёх ключевых компонентах:

- **Multi-Head Latent Attention (MLA)** — механизм внимания, который сокращает затраты памяти на хранение KV-cache во время генерации текста.
- **DeepSeekMoE** — архитектура Mixture of Experts (MoE), позволяющая активировать только часть параметров модели для обработки каждого токена.
- **Multi-Token Prediction (MTP)** — дополнительная обучающая задача, при которой модель учится предсказывать несколько следующих токенов, а не только один.

Модель содержит **671 млрд параметров, из которых для обработки каждого токена активируется около 37 млрд**.

### 1.1. Общая структура Transformer-блока

В упрощённом виде модель состоит из множества последовательно расположенных Transformer-блоков.

В каждом блоке есть два основных вычислительных компонента:

1. **Attention (MLA)** — позволяет токенам учитывать информацию из предыдущих токенов последовательности.
2. **Feed-Forward Network (FFN/MoE)** — преобразует представления токенов с помощью нейронных сетей.

Между компонентами используются нормализация RMSNorm и остаточные соединения (residual connections).

### 1.2. Общая схема обработки текста

```text
Входной текст
     ↓
Токенизация
     ↓
Представления токенов (Embeddings)
     ↓
┌──────────────────────────────┐
│       Transformer-блок       │
│                              │
│  RMSNorm                     │
│     ↓                        │
│  MLA (Attention)             │
│     ↓                        │
│  Residual Connection         │
│     ↓                        │
│  RMSNorm                     │
│     ↓                        │
│  DeepSeekMoE                 │
│     ↓                        │
│  Residual Connection         │
└──────────────────────────────┘
     ↓
Повторение блоков
     ↓
Выходные представления
     ↓
Логиты → Softmax
     ↓
Распределение вероятностей
     ↓
Предсказание следующего токена
```

## 2. Multi-Head Latent Attention (MLA)

**MLA — это модифицированный механизм внимания, который сокращает объём памяти, необходимый для хранения Key-Value Cache во время генерации текста.**

Обычный механизм внимания использует три представления каждого токена:

- **Query (Q)** — какую информацию ищет текущий токен.
- **Key (K)** — по каким признакам другие токены могут быть найдены.
- **Value (V)** — какую информацию токены передают при взаимодействии.

### 2.1. Как работает механизм внимания?

В упрощённом виде процесс выглядит так:

1. Модель вычисляет Query для текущего токена.
2. Сравнивает его с Key предыдущих токенов.
3. Преобразует результаты сравнений в веса внимания с помощью Softmax.
4. Использует полученные веса для взвешенной суммы Value.
5. Передаёт результат дальше по сети.

В обычном Multi-Head Attention (MHA) используются несколько голов внимания. Каждая голова имеет собственные проекции Q, K и V и может учиться учитывать разные аспекты контекста.

### 2.2. Что такое KV-cache и почему он занимает много памяти?

При авторегрессионной генерации модель выдаёт текст по одному токену за раз.

Пример последовательной генерации:

```text
Шаг 1: The
Шаг 2: The cat
Шаг 3: The cat sat
Шаг 4: The cat sat down
```

На каждом шаге модели необходимо учитывать предыдущие токены.

Если каждый раз заново вычислять Key и Value для всей последовательности, это приведёт к повторным вычислениям.

Для ускорения генерации модель сохраняет уже вычисленные Key и Value в специальной памяти — **KV-cache**.

На следующем шаге она вычисляет представления нового токена и использует ранее сохранённые значения.

Однако с увеличением длины контекста растёт объём KV-cache. В большой модели с множеством слоёв и голов внимания это может стать серьёзным ограничением.

### 2.3. Как MLA решает эту проблему?

Вместо того чтобы сохранять полные Key и Value для каждой головы внимания, MLA **совместно сжимает информацию, необходимую для их формирования, в компактное латентное представление**.

Это ключевая идея MLA, описанная в разделе 2.1.1 статьи.

#### Схема сжатия Key-Value представлений

```text
Входное представление токена h
              ↓
      Сжатие (Down-Projection)
              ↓
      Компактный латентный
         вектор c_KV
              ↓
        ┌─────┴─────┐
        ↓           ↓
 Восстановление  Восстановление
      Key             Value
        ↓           ↓
 Key для голов   Value для голов
   внимания         внимания
```

## 3. DeepSeekMoE

**DeepSeekMoE — это архитектура Mixture of Experts (MoE), в которой для обработки каждого токена выбираются только некоторые нейронные сети-эксперты.**

Основная идея заключается в том, чтобы увеличить общую ёмкость модели, не активируя все её параметры при обработке каждого токена.

### 3.1. Что такое Mixture of Experts?

В обычном Transformer-блоке FFN (Feed-Forward Network) обрабатывает представление каждого токена.

В архитектуре MoE вместо одной общей FFN используется несколько специализированных сетей — **экспертов (Experts)**.

#### Схема работы MoE

```text
                  Входной токен
                        ↓
                      Router
                        ↓
             Выбор подходящих экспертов
                        ↓
              ┌─────────┼─────────┐
              ↓         ↓         ↓
          Эксперт 1  Эксперт 2  Эксперт 3
              ↓         ↓         ↓
              └─────────┼─────────┘
                        ↓
               Объединение выходов
                        ↓
                Выходное представление
```

**Router (маршрутизатор)** определяет, какие эксперты будут обрабатывать конкретный токен.

DeepSeekMoE использует две важные идеи.

#### 1. Fine-grained Experts — большое количество небольших экспертов

Вместо небольшого количества крупных экспертов используются многочисленные более мелкие эксперты, из которых маршрутизатор выбирает ограниченное число.

Это позволяет гибче комбинировать экспертов для обработки разных токенов.

#### 2. Shared Experts — общие эксперты

Помимо выбираемых маршрутизатором экспертов, существуют общие эксперты, которые активируются для каждого токена в соответствующем MoE-слое.

Их назначение — обрабатывать знания и закономерности, которые полезны для многих токенов, уменьшая необходимость повторять одинаковые функции во множестве маршрутизируемых экспертов.

### 3.2. Auxiliary-loss-free load balancing

**Auxiliary-loss-free load balancing** — дополнительный механизм, который DeepSeek-V3 использует для балансировки нагрузки между экспертами.

Проблема заключается в том, что маршрутизатор может слишком часто выбирать одних экспертов и редко — других. В результате часть вычислительных ресурсов используется неравномерно.

Для решения проблемы авторы применяют стратегию балансировки без дополнительной функции потерь, специально предназначенной для балансировки нагрузки. Вместо неё используются корректировки смещений маршрутизации экспертов.

Это важно, поскольку традиционные вспомогательные функции потерь для балансировки могут негативно влиять на качество модели.
